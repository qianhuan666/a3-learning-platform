# Database Structure And Button Bindings

This project keeps layout state, business records, and derived dashboard data separate.

## Core Permission Model

- `user_accounts`: login accounts.
- `account_user_links`: maps an account to the student profile.
- `account_portal_permissions`: currently keeps a single student portal permission path so login and write checks stay explicit.
- `v_account_portals`: server-side permission view used by every API request.

The demo student request uses `portal=student&account=student_demo`. The product is now student-portal only; teacher and parent demo accounts have been removed from active seed data and non-student portal dashboard access returns `404`.

## Button Write Tables

- `student_activity_events`: append-only click/audit events for navigation, search, tab switches, hint toggles, and other lightweight actions.
- `student_ui_state`: latest UI state per student/course/portal/page, such as active page, selected course, resource filters, plan date, expanded panels, report tab, and hint-open state.
- `student_learning_sessions`: records each "start learning" or "review task" entry, linked to `study_plans` when the button is launched from a plan task.
- `student_resource_usage`: records resource card actions, linked to `learning_resources`.
- `report_exports`: records each report export request and its metrics payload.
- `study_plans`: stores plan tasks created/deleted by the learning plan page.
- `chat_sessions`, `chat_messages`, `chat_guidance_steps`, `chat_action_logs`: store the AI tutor conversation, long message history, guidance steps, and quick-action usage.
- Resource integration tables now sit behind resource cards: `resource_sources`, `resource_ingestion_batches`, `course_knowledge_points`, `resource_knowledge_links`, `learning_resource_versions`, `resource_chunks`, `resource_distillations`, `question_items`, and `student_question_attempts`.

## API Binding Map

- Sidebar and top navigation: `POST /api/ui-state`, `POST /api/activity-events`.
- Course switch, search, notices, profile menu: `POST /api/ui-state`, `POST /api/activity-events`.
- Home "start learning" and task buttons: `POST /api/learning-sessions`, `PATCH /api/plans/:id/status`, `POST /api/ui-state`, `POST /api/activity-events`.
- Profile insight/knowledge/trend toggles: `POST /api/ui-state`, `POST /api/activity-events`.
- Plan date, add/delete/status plan, adjustment switches: `GET /api/plans`, `POST /api/plans`, `PATCH /api/plans/:id/status`, `DELETE /api/plans/:id`, `POST /api/ui-state`, `POST /api/activity-events`.
- Resource filters, sort, batch, card action: `GET /api/resources`, `GET /api/resources/:id`, `GET /api/resources/:id/file`, `POST /api/resources/:id/usage`, `POST /api/ui-state`, `POST /api/activity-events`.
- Resource question practice: `GET /api/questions`, `POST /api/question-attempts`, backed by `question_items` and `student_question_attempts`.
- AI tutor new session, messages, quick actions, hints: `POST /api/tutor/sessions`, `POST /api/tutor/messages`, `POST /api/tutor/actions`, `POST /api/ui-state`, `POST /api/activity-events`.
- Report tabs/details/export: `POST /api/ui-state`, `POST /api/report-exports`, `POST /api/activity-events`.

## Derived Data

The frontend should not store these computed values:

- Dashboard progress and report metrics: derived from `learning_metric_daily`, `learning_tasks`, and `study_plans`.
- Profile radar and mastery bars: derived from `student_profile_scores`.
- Heatmap: derived from `knowledge_mastery`.
- Resource ordering: read from `learning_resources` plus `student_resource_recommendations`, then refined later with `student_resource_usage`.
- Resource explanations, tutor context, practice plans, and misconception hints: derived from `resource_chunks`, `resource_knowledge_links`, `resource_distillations`, `question_items`, and `student_question_attempts`.
- Tutor conversation screen: read from `chat_sessions`, `chat_messages`, and `chat_guidance_steps`.

Temporary browser-only state is limited to unsent input text, hover/focus state, and scroll position.

## Learning Session Completion Loop

The learning flow is now a closed local-data loop instead of a one-way "start learning" event.

- Start: task buttons, resource learning buttons, and plan rows call `POST /api/learning-sessions`.
- In progress: the frontend keeps only the current open task in React state so the tutor page can show context.
- Finish or pause: tutor context actions call `PATCH /api/learning-sessions/:id/finish`.
- Idempotency: if the same session is already finished, the API returns the stored session and does not add study minutes again.
- Plan linkage: sessions launched from `study_plans` update plan status to `active`, `done`, or `pending`.
- Resource linkage: sessions launched from `learning_resources` write `student_resource_usage`.
- Target-mode linkage: sessions store `goal_mode_id`; completed or paused sessions update `student_goal_modes.progress`.
- Report linkage: completed minutes, completion rate, accuracy fallback, questions done, and mistakes fixed are written to `learning_metric_daily`.
- Audit linkage: each completion state writes `sync_events` plus frontend `student_activity_events`.

Stored fields for the completion definition live in `student_learning_sessions`: `target_minutes`, `completed_minutes`, `completion_score`, `completion_definition`, `completion_reason`, `outcome`, `completed_at`, and `ended_at`.
